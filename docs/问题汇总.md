## 2026-06-25：企业端侧项目真实会用 Python 还是 C++？把智能冰箱改成 C++ 会不会刻意？

### 问题

智能冰箱当前是在 conda 的 Python/RKNN 环境下运行：

```bash
python3 main.py
python3 web_server.py
```

如果后续改成 C++ 或 Python+C++ 混合架构，会不会显得刻意？真实企业项目到底会用 Python 还是 C++？

### 结论

不刻意，但前提是不能为了换语言而换语言。

真实企业里常见分工是：

- Python：算法验证、Demo、调参工具、Web/API、测试脚本、日志分析。
- C/C++：摄像头采集、图像预处理、NPU 推理、后处理、多线程、IPC、长期运行服务。

所以合理路线不是“把整个智能冰箱全量 C++ 重写”，而是：

> 保留 Python 版完整业务闭环，抽取性能敏感的视觉推理主链路，用 C/C++ 重新实现。

### 后续行动

- 冻结当前 Python 版作为完整系统项目。
- 新增 C/C++ 推理核心模块，先打通图片/摄像头到 RKNN 推理再到 YOLO 后处理。
- 输出 FPS、推理耗时、检测 JSON，证明 C++ 化有工程价值。
- 后续让 rkd 托管 C++ 推理进程和 Python Web 服务。

## 2026-06-25：rkd 没有具体业务，面试官会不会觉得没用？

### 问题

rkd 是一个 C/POSIX 守护进程项目，功能是托管服务、异常退出重启、提供 UDS 控制命令。但它不像智能冰箱一样有具体业务，担心面试官觉得“没用”。

### 结论

rkd 本身不是没用，问题是不能孤立讲成“写了个守护进程练手”。

更好的定位是：

> 面向嵌入式设备的轻量级服务管理与故障恢复框架，用于托管摄像头采集、AI 推理、Web 服务等板端进程，提升设备长期运行稳定性。

这样它就和智能冰箱产生业务连接：

- 托管 C++ 推理进程 `fridge_infer`
- 托管 Python Web 服务 `web_server.py`
- 记录异常退出日志
- 支持 start/stop/restart/status/list
- 支持配置热加载和优雅退出

### 后续行动

- rkd 不要只做孤立工具，要绑定智能冰箱部署场景。
- README 中增加“托管智能冰箱服务”的示例配置。
- 后续将 rkd 作为 Linux 系统编程主项目。

## 2026-06-25：投递软件工程师岗位时，HR 追问在校、C++独立编程、软件项目经历，该怎么回复？

### 问题

- 有无参与过软件开发相关事项？

- 同时确认岗位实际内容是否涉及设备通信、图像处理、硬件联调、串口/USB、嵌入式设备。

## 2026-06-26：看到别人的 RK3568 视频流/检测管线项目，智能冰箱能不能改成类似形态？

### 问题

用户看到一个 RK3568/RK3588 风格的视频管线项目图，包含 V4L2 采集、帧环形缓冲、RKNN 检测、MPP H.264 编码、UDP/RTP 推流、PC 播放、模块化依赖图和部署拓扑图。用户希望判断智能冰箱项目是否也可以改成类似形式。

### 结论

可以借鉴，但不建议直接照搬全量功能。

该类项目本质是“嵌入式视频处理/推理/推流管线”，比当前智能冰箱更偏 C++、多线程、V4L2、RKNN Runtime、MPP、网络传输和性能优化。智能冰箱可以从中抽取一条 C++ 工程化主链路：

- V4L2/摄像头采集
- 帧缓冲队列
- RKNN 推理
- YOLO 后处理
- 耗时/FPS统计
- JSON/IPC 输出

但短期不应同时做 MPP 编码、RTP 推流、PC 播放器、完整网络协议和复杂可视化，否则容易变成新大坑。

### 后续行动

- 智能冰箱 Python 版继续保留为完整业务闭环。
- 新增 C++ 子项目，先做 “CaptureModule + DetectModule + ResultOutput”。
- 第二阶段再考虑 EncoderModule/StreamModule，用 MPP/H.264 和 UDP/RTP 推流作为加分项。
- 简历表述应强调“从原业务项目中抽象出端侧视觉推理管线”，而不是假装原项目一开始就是完整视频流系统。

## 2026-07-02：汽车称重/传感器采集/Qt 显示岗位是否值得去？RK3588 迁移是什么意思？

### 问题

用户面试了一家做传感器数据采集和 Windows Qt 界面的公司，业务类似汽车称重/超载检测。当前控制器为 FPGA，传感器连接 FPGA，数据库和通信协议不明确，Windows 端 Qt 做 UI 显示；后续计划迁移到 RK3588 Linux 端。用户担心入职后主要做 Qt 应用层，接触不到底层；同时公司不允许使用 AI 写代码，觉得效率低。

### 结论

该岗位不是典型嵌入式 Linux 底层岗位，更像“工业测控/称重系统上位机与设备软件”岗位。它的价值取决于实际工作是否能接触到：

- 传感器数据协议与通信链路。
- FPGA/控制器到上位机的数据格式。
- Qt 之外的设备联调、串口/TCP/UDP/数据库/日志。
- 后续 RK3588 Linux 迁移中的 Linux 部署、交叉编译、服务化、驱动/接口适配。

如果只做 Windows Qt 界面、表格、按钮和业务页面，对嵌入式 Linux 主线帮助有限；如果能参与通信协议、采集链路、RK3588 迁移和现场调试，则有一定价值。

### 后续行动

- 继续沟通时必须问清：实际工作中 Qt UI、通信协议、数据库、Linux/RK3588、现场联调各占比。
- 不要因为“不让用 AI”就直接否定岗位。企业不允许 AI 写业务代码主要考虑代码安全、合规、泄密和可控性；但可以用文档、手册、调试工具提升效率。
- 若入职，目标应争取从 Qt 扩展到设备通信、数据采集链路、Linux 迁移和系统稳定性，而不是长期只画界面。

## 2026-07-02：5k 的汽车称重 Qt/RK3588 岗和 3.5k 的医疗设备嵌入式岗怎么选？

### 问题

用户当前比较两个实习机会：

- 汽车称重/传感器采集公司：薪资约 5k，当前是 FPGA + Windows Qt 上位机，后续可能迁移到 RK3588 Linux。
- 医疗设备公司：薪资约 3.5k，做医疗监护/血氧/康复设备，可能偏 C 语言、单片机或医疗设备界面，尚不确定是否真正使用 Linux。

用户担心前者偏 Qt 应用层、后者可能偏单片机或界面，二者都不一定贴合嵌入式 Linux 底层主线。

### 结论

在信息未完全确认前，不能只按薪资选。优先级判断：

- 若汽车称重公司能参与 RK3588 Linux 迁移、设备通信协议、数据采集链路、数据库和现场联调，则优先级高于医疗设备公司。
- 若汽车称重公司只做 Windows Qt 界面，而医疗设备公司能做 C/Linux 或设备固件调试，则医疗设备更有长期价值。
- 若医疗设备公司主要是单片机 C 或界面维护，不涉及 Linux，且汽车称重公司有明确 RK3588 迁移计划，则选 5k 汽车称重更现实。

### 后续行动

- 必须向两家公司确认实际工作内容占比：Qt UI、通信协议、Linux/RK3588、C/C++、数据库、现场调试、驱动/单片机。
- 选择标准不是“底层不底层”的想象，而是能否形成下一份简历证据：C/C++、Linux、通信协议、设备联调、产品稳定性。

## 2026-06-27：如泰科技医疗设备嵌入式 Linux 岗位，智能冰箱项目如何重新包装？

### 问题

用户即将面试重庆如泰科技嵌入式 Linux 软件工程师实习。该公司主营数字医疗电子系统，包括监护仪、血氧仪、康复理疗仪、电子血压计和中央监护系统，并强调 CE/FDA/ISO 13485 等质量流程。用户担心智能冰箱项目与医疗设备业务不直接相关，想知道如何修改项目复盘讲法。

### 结论

不应把智能冰箱项目硬说成医疗项目，也不应夸大为驱动/BSP 项目。更合适的讲法是：

- 这是一个 RK3568 板端数据采集、处理、状态判断、数据持久化和 App 联调的完整嵌入式 Linux 系统原型。
- 与医疗设备岗位可迁移的能力是：连续数据采集、状态机稳定性、异常兜底、日志追溯、接口联调、板端部署和技术文档。
- 面试中应把重心从“AI 识别很准”转到“系统链路如何稳定运行、如何排查问题、如何按流程记录和验证”。
- rkd 项目用于补足 C/POSIX/Linux 进程管理能力，和冰箱项目形成“业务闭环 + 系统编程”的组合。

- 临场不要虚称做过医疗算法、驱动开发或医疗级可靠性；要强调自己能从模块维护、问题复现、日志分析、接口联调和测试文档做起。
