## 2026-06-25：明确 C++ 化方向不是全量重写，而是抽取端侧推理主链路

### 当前 Python 版启动方式

开发板进入 conda/rknn 环境后，在 `/root/2_deploy` 目录下启动两个独立进程：

```bash
python3 main.py
python3 web_server.py
```

当前运行关系：

```text
main.py
  ├─ 摄像头采集
  ├─ 运动门控
  ├─ 前后帧差分定位
  ├─ RKNNLite 推理
  ├─ YOLOv8 后处理
  ├─ 事件判断
  ├─ SQLite 库存写入
  └─ 写 /tmp/fridge_latest.jpg

web_server.py
  ├─ 读取 inventory.db
  ├─ 读取 /tmp/fridge_latest.jpg
  └─ 提供 Flask REST API

Android App
  └─ 访问 http://192.168.3.100:5000 的 API
```

这套 Python 版已经完成完整业务闭环，适合作为“端侧 AI 系统集成项目”和研电赛展示成果。

### 为什么不建议全量改成 C++

不建议把库存、Web、App、包装食品/OCR、人工修正等业务模块全部改成 C++。原因：

- 这些模块不是性能瓶颈，用 Python/Flask/SQLite 很合理。
- 全量重写成本高，容易破坏已经跑通的闭环。
- 企业真实项目里也常见“C++ 负责实时链路，Python/脚本负责业务服务、工具和调试”。
- 如果只是把 Python 逐行翻译成 C++，面试价值有限。

### 推荐的混合架构

推荐把 Python 版冻结为完整系统闭环，同时新增一个 C/C++ 推理核心模块：

```text
C++ fridge_infer
  ├─ 摄像头采集 / 图片输入
  ├─ 图像预处理
  ├─ RKNN Runtime 推理
  ├─ YOLOv8 后处理
  ├─ 耗时/FPS 统计
  └─ 输出 JSON / UDS / stdout

Python main.py 或上层服务
  ├─ 事件状态机
  ├─ 库存管理
  ├─ SQLite
  └─ REST API

rkd
  ├─ 托管 C++ 推理进程
  ├─ 托管 Web 服务
  └─ 负责异常退出后的重启和状态查询
```

### 分阶段目标

第一阶段：C++ 单图/回放推理链路

```text
图片输入 -> letterbox 预处理 -> RKNN Runtime -> YOLO 后处理 -> 打印检测结果
```

第二阶段：C++ 摄像头实时推理链路

```text
摄像头输入 -> 预处理 -> RKNN 推理 -> 后处理 -> FPS/耗时统计 -> 可视化或 JSON 输出
```

第三阶段：Python+C++ 混合部署

```text
C++ 负责实时视觉推理
Python 负责事件、库存、Web/API
二者通过 JSON 文件、Unix Domain Socket 或本地 HTTP 解耦
```

第四阶段：rkd 托管

```text
rkd 配置托管 fridge_infer 和 web_server
支持崩溃重启、状态查询、日志记录、优雅退出
```

### 技术决策

- 原 Python 项目不推倒重来，作为稳定闭环保留。
- C++ 化只针对性能敏感链路：摄像头采集、预处理、RKNN 推理、YOLO 后处理。
- 上层业务逻辑仍可由 Python 承担，避免为了“显得底层”而做无意义重写。
- C++ 模块必须提供可度量结果：推理耗时、FPS、失败处理、输出接口。

### 简历/面试可讲点

- Python 版用于快速完成端侧业务闭环。
- C++ 版用于抽取实时推理核心链路，贴近企业端侧部署方式。
- 混合架构体现模块边界：实时链路、业务服务、进程托管分层解耦。
- rkd 可作为系统稳定性组件，托管推理进程和 Web 服务。
