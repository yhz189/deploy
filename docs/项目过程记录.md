## 2026-06-04：恢复轻量 --show 显示模式

### 现象

回退到 `b522e66` 后，板端运行 `python3 main.py --show` 帧率明显下降。

### 根因

该版本中 `--show` 会每帧调用一次 `infer_full_frame()`，也就是为了在窗口上画实时 YOLO 框而额外跑完整模型。事件检测本身并不需要这一步，真正的取放识别仍然是运动门控稳定后再推理；低帧率主要来自显示调试叠加，不是主链路必须开销。

### 修改

- `--show` 默认只显示状态机、帧号、最近事件和变化区域框。
- 新增/恢复 `--show-infer` 作为调试开关，需要实时 YOLO 框时才启用。
- `SHOW_INFER_INTERVAL` 设为 5，避免打开调试框时每帧都跑全帧 YOLO。

## 2026-06-04：事件图、包装候选与鸡蛋 strict gate 收敛

### 背景

App 端事件详情看不到变化前后裁剪图，包装待确认栏还会显示很早以前的旧图；同时香蕉图片、包装图、局部图案有时会被鸡蛋专项计数误触发，导致库存出现错误的 egg 放入/取出记录。

### 决策

- `debug_crops` 不再保存 full、overview、raw、classified 等大量中间图，每次事件只保存最终变化区域的前后裁剪图。
- `metadata.json` 明确记录每个变化区域的 `before_file`、`after_file`、`before_url`、`after_url`，供 App 事件详情直接展示。
- 包装候选采用“新事件覆盖旧候选”，每次保存新入库候选或取出候选前先清理旧 `/tmp/fridge_package_candidate.*` 与 `/tmp/fridge_package_takeout*`。
- 鸡蛋 zoom-crop 自动计数继续保留，但加严格门禁：普通区域必须已有高置信 egg 证据、egg 面积不能过小、前后至少一侧达到鸡蛋盒规模、变化区域占比不能太小，否则跳过专项 delta。
- 普通 APPEAR/DISAPPEAR 中的 egg 结果也增加基础门禁，低置信或小面积 egg 区域直接忽略，避免 zoom-crop 被拦住后普通区域仍然误写 egg 库存。

### 修改

`main.py`：

- `save_change_debug_crops()` 只保存 `final_XX_ref.jpg` 与 `final_XX_new.jpg`，并在 metadata 中写入可映射 URL。
- 新增 `egg_evidence_stats()` 与 `pass_egg_strict_gate()`，未通过时打印 `[EGG] skip strict gate ...`，回退普通区域识别/候选逻辑，不更新 egg 库存。
- 新增 `suppress_weak_egg_regions()`，普通区域 egg 若低于 `conf>=0.55` 或 `area>=1500`，打印 `[EGG] skip weak region ...` 并忽略该区域。

`package_ocr.py`：

- `save_package_candidate()` 保存前调用 `clear_package_candidate()`。
- `save_package_takeout_candidate()` 保存前调用 `clear_package_takeout_candidate()`。
- 候选 metadata 保留 `ocr_required=true`、`auto_popup=false`、`status=pending_confirm`，明确由 App OCR/用户确认。

`web_server.py`：

- `/api/debug/events` 返回最近视觉事件列表，`crops[]` 内包含绝对 `before_url/after_url`。
- `/api/events` 的每条库存事件附带最近 debug 事件作为辅助，不再要求 App 只能从库存事件拿图片。
- 包装候选接口返回绝对 URL 与 `age_seconds`，并新增 DELETE 清除候选接口。

## 已确认的工程基线

### RKNN 版本与模型

当前主模型确定为：

```text
models/fridge_yolo_opset11_rknn16.rknn
```

板端推理框架确定为：

```text
rknn-toolkit-lite2 1.6.0
/usr/lib/librknnrt.so 1.6.0
```

重要排障结论：旧 RKNN 1.4.0 会导致 YOLOv8 bbox 坐标分支异常，表现为类别分数正常，但前 4 个 bbox 坐标大量为 0。这个问题不是后处理阈值问题，也不是摄像头问题，而是运行时版本与模型链路不匹配。后续不要回退到 1.4.0。

### YOLOv8 后处理约定

当前输出可能是：

```text
(1, 24, 8400)
(1, 24, 8400, 1)
```

统一解析为：

```text
(8400, 24)
```

前 4 个为 `xywh`，后 20 个为类别分数。当前类别数为 20，包含 `egg`。后处理不做 sigmoid，不乘 objectness。

### 预处理约定

当前 RKNNLite 输入为 RGB、uint8、NHWC 或 batch NHWC：

```text
(1, 640, 640, 3)
```

不要除以 255，不要传 `data_format='nchw'`。

## 鸡蛋计数专项

### 问题

普通 YOLO 检测对鸡蛋盒远距离、小目标、密集排列场景不稳定。19 个鸡蛋曾经只能数到十几个，且数量波动较大。

### 处理思路

没有为鸡蛋单独换一条完全不同的主流程，而是在事件变化区域基础上增加鸡蛋专项增强：

- 合并变化区域。
- 外扩 crop。
- 对 crop 放大后重新推理。
- 将鸡蛋置信度阈值降到 `0.10`。
- NMS 阈值放宽到 `0.75`。
- 用前后 crop 的鸡蛋数量差作为事件数量。

### 效果

远距离鸡蛋盒计数明显改善，19 个鸡蛋大约能数到 18 个。仍存在小目标漏检，因此报告中应诚实说明：鸡蛋计数属于小目标密集检测，当前可接受但不是绝对精确，保留用户修正兜底。

## 包装食品与本地大模型协同

### 初始目标

希望在 RK3568 端侧识别之外，引入局域网本地主机多模态模型，用来辅助识别：

- 包装食品。
- YOLO 低置信度目标。
- YOLO 明显误识别，例如黄色盒子识别成 banana。
- OCR 为空或文字混乱的包装。

### 架构决策

不能把核心能力全部交给主机大模型。最终确定为：

```text
RK3568 端侧：事件触发、变化区域定位、YOLOv8-RKNN 基础识别、库存更新
Windows 主机 VLM：低置信度/包装复杂/误识别兜底
App/用户：最后确认和修正
```

这样更符合赛题“端侧优先”的定位，也避免主机服务不可用时主流程崩掉。

### 当前实现

新增：

```text

local_vlm_client.py
test_local_vlm_client.py
docs/局域网本地大模型协同识别方案.md
```

当前服务端支持：

- `mock` 后端：用于链路验证。
- `ollama` 后端：用于后续接本机视觉模型。

API：

```text
POST /api/vlm/recognize
```

返回结构：

```json
{
  "name": "纸巾",
  "category": "package",
  "count": 1,
  "confidence": 0.82,
  "source": "local_vlm",
  "reason": "图中是白色包装纸巾"
}
```

### 重要教训

mock 后端不看图片，只看文件名、hint 或 prompt 中的关键词。曾经为了联调设置 `LOCAL_VLM_HINT=hotpot`，导致任何手影或噪声都被 mock 成火锅底料并入库，污染了库存。

因此后来改为：

- 主流程默认不读取 `LOCAL_VLM_HINT`。
- 只有显式设置 `LOCAL_VLM_ALLOW_MOCK_HINT=1` 时才允许 mock hint 影响主流程。
- mock 只用于验证链路，不用于评价真实识别能力。

## 摄像头事件稳定性与 OpenCV 变化区域

### 现象

用户测试时，只是在镜头前挥手，系统也检测到变化区域，并触发包装候选甚至库存变化。日志中常见变化框位于画面边缘，例如：

```text
(534, 0, 103, 40)
(557, 0, 83, 95)
```

这类区域并不是真实物品取放，而是手影、边缘残留或动作未完全稳定造成的变化。

### 判断

主要有两个原因：

1. 事件分析使用的后帧可能太早，动作刚结束但画面还没真正稳定。
2. NOISE 区域被过度信任，进入 OCR/VLM 或包装取出匹配。

### 修改

在 `event_detector.py` 中调整：

- `SETTLING` 阶段持续更新后帧。
- 等稳定帧数满足后，使用最后一张稳定帧进行分析。
- 默认 `settle_frames` 从 5 增加到 12。

在 `main.py` 中增加过滤：

- 小面积变化过滤。
- 贴边局部变化过滤。
- NOISE 默认不自动扣生鲜库存。
- 包装出库默认不靠 bbox 重叠直接扣库存。

### 效果

后续挥手测试中，系统仍可能进入 `BUSY`，但最终只打印 `[FILTER]`，不再修改库存。这说明运动门控仍然能感知动作，但库存层已经更保守。

## YOLO 误识别与低置信度策略

### 问题

橙色眼镜盒、黄色盒子等非训练物体可能被 YOLO 识别成 banana/carrot。曾出现：

```text
banana conf=0.360
carrot conf=0.239
```

如果直接相信这些结果，会把非食品误入库，或者取出时错误扣库存。

### 决策

当前阶段优先追求“不要乱改库存”，而不是“所有东西都自动识别”。因此采取保守策略：

- YOLO 低置信度生鲜不直接入库。
- 低置信度 `DISAPPEAR` 不直接扣库存。
- 低置信度或未知变化保存为包装/OCR/VLM 候选。
- 等真实本地 VLM 接入后，再让 VLM 负责判定“这是纸巾/包装/非食品/水果”。

### 效果

后续测试中：

- 挥手不再入库/出库。
- 包装和未知物体进入候选，不直接污染库存。
- 库存稳定性明显提升。

## 包装出库策略

### 问题

历史 mock 写入的火锅底料带有 bbox。之后只要 NOISE 区域与该 bbox 重叠，系统就可能自动扣火锅底料库存，即使实际测试的是纸巾或手影。

### 决策

默认关闭包装 bbox 自动出库：

```bash
unset AUTO_PACKAGE_TAKEOUT
```

只有显式设置时才启用：

```bash
export AUTO_PACKAGE_TAKEOUT=1
```

当前比赛联调阶段建议保持关闭，让包装取出先进入候选，由 OCR/VLM/用户确认后再写回。

### 效果

避免了“历史 bbox 污染导致错扣包装库存”的问题。代价是包装取出暂时不完全自动，但系统更稳，更适合演示和测试记录。

## 赛题答辩口径沉淀

### 端侧优先

系统的核心不是“把图片发给大模型识别”，而是：

- RK3568 端侧负责事件触发。
- RK3568 端侧负责基础 YOLOv8-RKNN 识别。
- 主机 VLM 只处理低置信度、包装复杂、OCR 失败、明显误识别场景。

### 分割能力

当前没有真正训练 YOLO-seg，也没有 mask 标注数据。因此不能声称已经实现深度实例分割。更合理的低风险方向是：

- YOLO 检测框。
- 前后帧变化区域。
- OpenCV 连通域/轮廓/GrabCut/Watershed 二阶段辅助。
- 分割只辅助判断多目标、紧贴、遮挡、面积变化，不替代 YOLO 分类。

### 低算力说明

系统不是每帧都跑完整模型，而是运动门控加稳定后事件触发推理，因此实际核心计算需求远低于持续每帧检测。报告中应强调：

- YOLOv8n-RKNN 是轻量目标检测模型。
- RKNNLite 是 RK3568 平台上的轻量端侧推理框架，定位类似 TFLite/NCNN/MNN，但本项目实际使用 RKNNLite。
- 不要声称实测过 TFLite/NCNN/MNN。

- OpenCV 变化区域参数最终取值。
- App 端本地 VLM 确认流程是否接入。

## 2026-06-03：放弃本地 VLM 路线并定向清理

### 背景

曾尝试在 Windows 主机上部署本地多模态模型，让 RK3568 通过局域网调用主机 API，对包装食品、低置信度目标和明显误识别场景做兜底识别。链路层面已经验证过板端可以上传裁剪图到主机接口，但真实模型部署阶段遇到明显工程风险。

### 放弃原因

- `qwen2.5vl:3b` 虽然能下载，但运行时提示系统内存不足。
- 本地 VLM 推理慢，包装文字和 OCR 类识别不稳定。
- 比赛演示优先保证 RK3568 端侧 YOLOv8-RKNN 主流程稳定。
- App 侧已关闭对 `192.168.3.5:8001/api/vlm/recognize` 的实际调用，只保留包装候选确认/编辑流程。

### 清理决策

本地 VLM 不再作为当前比赛演示路径。项目主线收敛为：

```text
RK3568 端侧 YOLOv8-RKNN
  + 运动门控
  + 前后帧变化区域
  + SQLite 库存增量更新
  + 包装候选图保存
  + App OCR/用户确认编辑
```

删除或移除：

- `local_vlm_server.py`
- `local_vlm_client.py`
- `test_local_vlm_client.py`
- `docs/局域网本地大模型协同识别方案.md`
- `main.py` 中自动调用本地 VLM 的逻辑

保留：

- 事件稳定性改动。
- `debug_crops` 调试图机制。
- 低置信度 YOLO 不直接入库/出库的保守策略。
- 包装取出默认不靠 bbox 自动扣库存的策略。
- App OCR/用户确认作为包装食品主兜底流程。

### 当前效果

清理后系统不再依赖 Windows 主机 `8001` 端口，也不需要 Ollama 或本地多模态模型。包装食品识别回到候选图 + App 侧确认/编辑流程，演示风险更低，端侧主流程更清晰。

### 后续注意

如果未来硬件资源更充足，仍可以重新设计本地 VLM 作为扩展功能，但不能影响当前 RK3568 端侧主链路。重新接入前必须先完成独立模型性能评估，再考虑写回库存。

## 2026-06-04：收紧变化候选与 App 确认体验

### 现象

现场测试发现 OpenCV 变化框有时偏大，边缘可能包含未变化的蔬菜水果，导致 YOLO 在裁剪图中识别到无关目标。另一个问题是轻微光照变化、手影或很小区域变化也可能生成包装候选，App 端随后弹出包装确认窗口，用户体验像是系统“过度打扰”。

同时发现包装取出候选的前后图在 App 端显示容易搞反；用户还希望点击事件时能看到本次动作的前后变化图和裁剪图，便于确认到底放入或取出了什么。

### 判断

问题不在库存数据库，而在“候选生成”和“候选展示”两层：

- OpenCV 普通变化框外扩偏大。
- 包装候选只看 bbox 面积和位置，缺少变化强度校验。
- App 把候选当成立即弹窗，而不是待确认队列。
- 后端只保存了 `debug_crops`，但没有给 App 暴露正式接口。

### 修改

收紧 `change_locator.py`：

- 普通变化框外扩从 25% 降到 12%。
- 最小外扩从 24px 降到 12px。
- 差分阈值从 30 提到 35。
- 最小轮廓面积从 400 提到 700。

增强 `main.py` 包装候选过滤：

- 增加变化强度判断：候选区域内必须有足够比例的像素发生明显变化。
- 增加平均差异阈值，过滤弱光照变化。
- 继续保留小区域、边缘局部变化过滤。

增强 `package_ocr.py`：

- 包装放入/取出候选增加：
  - `status=pending_confirm`
  - `auto_popup=false`
  - `confirm_mode=manual`
- 包装取出候选增加明确字段：
  - `before_image_url`
  - `after_image_url`
  - `before_label=取出前`
  - `after_label=取出后`

增强 `web_server.py`：

- 新增 `/api/debug/events`，返回最近的事件分析图。
- 新增 `/debug/events/<event_id>/<filename>`，用于获取 `overview/ref_full/new_full/final_xx_ref/final_xx_new/metadata.json`。
- `/api/events` 中尝试按时间匹配最近的 debug 事件，并附加 `debug` 字段，方便 App 事件详情页展示前后变化图。
- 新增 `/package/takeout/before_image` 和 `/package/takeout/after_image`，避免 App 混淆 ref/new。

### 效果预期

- 轻微光照变化更不容易生成包装候选。
- 普通变化框更贴近实际变化区域，减少包含无关物品的概率。
- 包装候选不再建议自动弹窗，而是进入“库存-包装-待确认”列表。
- 用户点击事件时，App 可以展示该事件对应的前后全图、变化概览图和裁剪图。

### 验证

PC 端已运行：

```bash

python -m pytest tests/ -q
```

结果：

## 2026-06-04：候选旧图、黑图与 App OCR 分工修正

### 现象

App 端进入事件详情后看不到动作前后的裁剪图；库存页“包装待确认入库”显示的是很早之前的旧裁剪图。包装取出待确认的两张图在黑色鼠标垫背景下可能都是黑图，导致用户无法判断。另一个交互问题是：候选确认页要求用户手动输入包装名称，看起来像手机 OCR 没有发挥作用。

同时，食材数量旁边的加减号每点击一次就调用一次库存修正接口，导致事件栏新增多条手动修正事件，不符合“用户一次修改只记一条事件”的预期。

### 判断

- 板端当前只保存“最新一个包装候选”，如果 App 不确认也不清除，就会一直显示旧图。
- 后端之前返回的是相对图片路径，Android 如果没有正确拼接主机地址，事件详情图可能加载不出来。
- 包装取出候选缺少明确的 `before/after` 字段，App 容易把 ref/new 理解反。
- 手机 OCR 应该在 App 端对候选图执行，并把识别结果预填到名称输入框；板端只负责提供裁剪图和写回接口。
- 数量加减应先改本地 UI 状态，用户点“保存/确认”时再调用一次接口。

### 修改

增强 `main.py`：

- 对包装候选增加内容质量过滤。如果取出前后 crop 都接近纯黑背景、纹理很低，则不生成包装候选。

增强 `package_ocr.py`：

- 包装候选增加 `ocr_required=true`。
- 增加 `name_source=app_ocr_or_manual`，提醒 App 先 OCR，失败再手动。
- 放入候选标记 `candidate_type=package_put_in`。
- 取出候选标记 `candidate_type=package_takeout`。

增强 `web_server.py`：

- 候选接口返回绝对 URL，Android 可直接加载：
  - `/api/package/candidate`
  - `/api/package/takeout_candidate`
- 候选接口增加 `age_seconds`，App 可提示候选是否过旧。
- 新增清除候选接口：
  - `DELETE /api/package/candidate`
  - `DELETE /api/package/takeout_candidate`
- 新增事件调试详情接口：
  - `GET /api/debug/events`
  - `GET /api/debug/events/<event_id>`

### App 侧应配合

- “包装待确认”不自动弹窗，放到库存页的待确认区域。
- 进入候选详情后，先对候选图执行手机 OCR，预填包装名称；OCR 失败再要求用户手动输入。
- 用户点击“忽略/清除候选”时调用 DELETE 接口，避免旧图长期残留。
- 事件详情页如果 `/api/events` 没有 debug 图片，应从 `/api/debug/events` 展示视觉事件记录。
- 数量加减按钮只改本地状态，点“保存”时再 POST 一次 `/api/stock/adjust` 或 `/api/package/adjust`。

## 2026-06-04：精简 debug_crops 与鸡蛋计数误触发修正

### 现象

连续用香蕉图片模拟放入/取出时，系统日志出现：

```text
[EGG] zoom-crop count: 5 -> 0, delta=-5
[事件] TAKE_OUT {'removed': {19: 5}}
```

画面里并没有鸡蛋，但库存被扣了 egg。另一个问题是 `debug_crops` 下每次事件保存了 full、overview、raw、classified、final 多套图片，目录越来越多，App 端也难以知道应该展示哪几张。

### 判断

鸡蛋专项计数逻辑对“单边为 0”的场景太激进。它本意是用于鸡蛋盒数量差分，但如果大 crop 中出现了低阈值假阳性 egg，且另一帧没有检测到 egg，就会把非鸡蛋事件误判成取出鸡蛋。

debug 图方面，比赛演示和 App 事件详情真正需要的是“每个变化区域的动作前/动作后裁剪图”，不需要保存大量中间调试图。

### 修改

`main.py`：

- `save_change_debug_crops()` 改为只保存最终变化区域的前后裁剪图：
  - `final_01_ref.jpg`
  - `final_01_new.jpg`
  - 多个变化区域则依次保存 `final_02_ref/new`。
- 保留 `metadata.json`，记录 bbox、kind、before/after 文件名。
- 新增 `has_egg_evidence()`。
- 鸡蛋专项计数如果出现“前后有一边 egg 数量为 0”，必须同时满足普通变化区域里已有 egg 证据，否则跳过该鸡蛋 delta，避免香蕉、手影、包装图误扣 egg。

`web_server.py`：

- `/api/debug/events` 改为优先返回最终裁剪图 `crops[].before_url/after_url`。
- full/overview 图变成可选字段，若文件不存在就不返回，避免 App 加载 404。

PC 端已运行：

```bash

python -m pytest tests/ -q
```

结果：

### 本地 VLM 方案阶段性结论

- `qwen2.5vl:3b` 虽然下载成功，但运行时报错：`model requires more system memory (6.9 GiB) than is available (5.7 GiB)`，说明 Windows 主机当前可用内存不足，终端和 GUI 都难以稳定加载模型。
